# Config

Layers compose user, project, then local into `EffectiveConfig`. Consume that result rather than recomposing files, and never save it back to a source file: use the existing save path, which patches the authored TOML and verifies the result so unknown keys and comments survive.

`Config`, `Settings`, the overlays and `ModelAlias` are `mars_schema::config` and `mars_schema::alias`, re-exported here: the WASM `read('mars.toml')` shares them, so a new key or rule goes there (see that crate's `AGENTS.md`). Only what touches disk, the harness registry (`targets.rs`), the local and user files and layering stay here.

Model aliases and skill/agent overlays replace by key. An agent's network host sets compose across project and local layers; scalar fields in the local agent entry replace the project entry, and tool rule entries merge by key. Preserve absent versus explicitly empty.

`mars_schema::config::read_consumer` (for `mars.toml`, which also returns its refusals) and `read` (the local and user files) are the readers of all three files; this module loads the file, words its error as `failed to parse <path>: …` and adds the file name to the notes (`project_config_diagnostics`). Serde reads the keys Mars knows; every key it leaves unread becomes one `field.unknown` that names file, table and key, and stays in the file. In the project's `mars.toml` and `mars.local.toml` it is a `Warning` (`unknown.rs`), because a misspelt `targets` leaves no targets and the sync removes what Mars installed there; the warning names the closest key the table reads (`target` → `targets`), found from the serde field list of the struct, not a key list kept here. In the user's `config.toml` and in a package it stays `Info`. Nothing here names a key, except `managed_root`, a retired one: its two fields exist only so a warning can name the `targets` to write from its value, and nothing reads it as a target (`effective_links` reads `targets` alone). Each file that has it warns `field.retired`, one message built from that file alone (`mars_schema::retired::config_notes`, which `read` and `read_consumer` share), so the CLI and the WASM reader say the same thing. `link` and `init` drop the key from `mars.toml` when they write `targets`, so the natural fix clears the warning; no other writer touches it. Delete the key, its two fields and the note once the warning is no longer wanted. Otherwise a key Mars once read and deleted is an unread key like a typo, and a bad value of a key Mars reads fails the load at its line (the whole-file error, `ConsumerRead::parse_error`: the schema also reads each table alone for the WASM, and the CLI refuses the project's own file whole). Don't add a per-key check or advice, a `flatten` map for unknown keys (it loses the line of a bad value) or a second parse path: a new key is a struct field, and a file Mars reads goes through `parse_config` or `parse_local` so `save` and `save_local` refuse what a load would. The underscore spellings `network_allow`, `network_deny`, `model_invocable` and `user_invocable` are serde aliases: 0.30.1 read them, and an ignored `network_deny` would drop a restriction without a line. The user config does not read `targets` or `[overrides]`; `user.rs` clears them and reports each as unread. `min_mars_version` parses as `requires-mars` does (`mars_schema::config::parse_min_mars_version`) and a value that does not fails the load of its file. A file's version floor comes from the key table (`mars_schema::keys::floor`, over `keys::used`), is set when the file is read, and `floor_warning` warns when the file does not state it, only above the first Mars that reads `min_mars_version`; it never writes the file. `targets` in `mars.local.toml` alone has a row (`Surface::LocalSettings`, read through `keys::Document::Local`), since Mars before 0.39.0 reads it as the whole list. The floor stays a `Warning` because ignoring it costs a teammate's older Mars a dropped restriction. Plugin-only metadata stays raw at load so invalid publication metadata can't block sync; plugin build validation checks it.

Only known harness targets grant routing permission. Generic targets and paths materialize content without granting harness access; an explicitly empty scope must not become unrestricted. See [config contracts](.context/CONTEXT.md).
