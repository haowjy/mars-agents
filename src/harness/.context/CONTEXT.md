# Harness runtime descriptors

`mars-schema` owns harness identity; the runtime registry is the one row per harness (its class: native provider and auth-status command, or probe spec; and `launched_by_meridian`, which makes `agent_emission = "auto"` write the native agents of a harness Meridian does not launch even under `MERIDIAN_MANAGED=1`, and is the second reader: `takes_provided` names the targets that get a host's provided skills, hooks and MCP servers), and owns provider affinity and candidate order. Routing never selects a harness whose row has `launched_by_meridian: false` (the filter is `routing::permission_denial`; a named one is skipped with a trace diagnostic or the `not_launched_by_meridian` skip reason). `mars-schema` holds the host row (display name, tool table, MCP naming, effort levels). Facts derivable from `HarnessId` are not stored: the executable is `id.as_str()`, the target directory is `.{id}` (`HarnessId::target_dir`), and the skill variant key is `id.as_str()`. Lowering policy is a table in `src/compiler`, so `src/harness` never depends on the compiler. Keep those authorities shared so callers do not disagree about valid harnesses or routing order.

A capability session retains the probe outcome and its observation together. Re-reading the cache while formatting the same command could pair a decision with a different refresh's timestamp or error. Windows `.cmd` and `.bat` executable lookup belongs to the platform resolver; do not duplicate its suffix handling.
