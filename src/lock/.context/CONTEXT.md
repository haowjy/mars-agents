# Lock ownership

Each output is identified by target root and destination. The same source can lower to different bytes on different targets, so canonical diff must compare the `.mars` checksum, and target mutations must use the matching target's claim. See [surface ownership](../../surface_ownership/.context/CONTEXT.md) for the distinction between installed and pending-deletion claims.

Older v2 item checksums cannot distinguish installed content from deletion tombstones. Loading retains dependencies and aliases but drops item and config-entry claims with a warning; unclaimed files remain local until explicitly adopted. Config entries without recorded emitted content are also dropped because Mars cannot distinguish them from user entries.

Marketplace plugin locks record the marketplace and plugin content identities separately. The content commit is replayed only while the marketplace commit and plugin source still match; otherwise the source must be resolved again. This prevents a changed marketplace entry from pinning content from the previous source.

A sync plans, writes and removes only the records of the targets it manages (`.mars` always). `LockFile::split_targets` (`lock/targets.rs`) cuts the lock it reads into the records that serve those targets and `rest`, the records that serve any other target, so no step of the sync can plan, prune or compare against a record outside its targets. The sync cuts `rest` again by whether a config file names the target: a named one (retired `.cursor`, or left out by `mars.local.toml`) is `carried`, and `merge_targets` joins it back into the lock the sync writes, after the last comparison; an unnamed one is `dropped`, and `target_sync::removal::remove_served` removes it, as `mars unlink` does. `provided_entries` (which config entries `machine.lock` holds) splits and joins with the records; `remove_served` restores the pair of a record it puts back. A record serves one target: an item that installs one copy per target (`hook/x@claude`) serves it whole, its `.mars` copy and its no-output record included; any other item's output serves its `target_root`. A local-only target (named only in `mars.local.toml`) has its records in the committed lock, so a teammate's sync removes them and the lock flips between machines; keeping them in `.mars/machine.lock` is not built. `write` sorts each item's outputs by `(target_root, dest_path)`, so a split and join changes no byte. A target Mars stopped supporting (`mars_schema::retired::RETIRED_TARGETS`: `.cursor`) is not special: it has no adapter, so `target::keyed_sections` reads the MCP file the retired entry names and `compiler::config_entries::hook_file` its hook file, which is all the removal needs to find what the lock records there.

An item with no outputs is gone, except a hook on a managed target that takes none of it (`hook/<name>@<target>`): it has nothing to write there, and its record is what tells the next sync the loss is not new. `link` and `unlink` do not call `finish`: every item keeps its `.mars` output through them, and only a sync knows which hook records stay. Only `LockFile::finish` prunes, once, after every output change; a reducer that removes an output must not prune items, or it drops that record on any sync that removes a file. `finish` also names `_self` under `[dependencies]` whenever an item has that source.
