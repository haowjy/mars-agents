# Sync

Sync resolves the complete desired package graph before compiling or changing installed content. Recovery commands may persist the user's config intent and stop before compilation when a hook uses an unreadable schema: the compiler must never receive a partial graph, or pruning and ownership become unsafe. Repair leaves a corrupt lock untouched until a complete sync can replace it.

New canonical outputs are journaled before they are written. Recovery checks the journal against the prior lock and the filesystem and fails closed on changed content or unsafe paths. `recovery::publish` publishes ownership (`mars.lock`, then the best-effort `.mars/native-agents.json` projection of it; a failed projection is only a warning) before removing the journal. Every command that writes `mars.lock` (`sync`, `link`, `unlink`, `resolve`) recovers the journal when it loads the lock and publishes through `publish`; one that doesn't wedges every later sync. Native and config outputs aren't journaled, nor is `--force` adoption of existing outputs: after a failed apply it needs `--force` again. See [recovery.rs](recovery.rs).

Dry runs must not create project state: they use scratch staging and acquire an existing sync lock without creating one. Every new write phase must honor dry-run mode.

A package may replace a provided canonical item: provider ownership is recognized alongside lock ownership, so host-specific provided items don't change the package lock. A host's hooks and MCP servers enter a sync as the dependency `_provided-<provider>` and its skills as outcomes from `provided::skill_outcomes`; the lock writes their records to `.mars/machine.lock`, never `mars.lock`. See [provided](../provided/.context/CONTEXT.md). See [ownership.rs](ownership.rs) and [validate.rs](validate.rs).

Sync plans, writes and removes only the records of the targets it manages. `load_config` splits the lock (`LockFile::split_targets`) twice: the pipeline holds only the managed targets' records in the lock it reads and the lock it builds; `carried` holds the records of a target a config file names but the sync does not manage (retired `.cursor`; `mars.local.toml`'s `targets` adds to the project's, so no other named target is unmanaged), which `finalize` joins back (`merge_targets`) after `settle`; `dropped` holds the records of a target no config file names, which `finalize` removes through `target_sync::removal::remove_served`, the code `mars unlink` runs, before the lock is published. Compare and prune only through that split: a record the pipeline never holds can't be taken for news or deleted. Don't add a second path for a target Mars stopped writing: it is this one. `--frozen` refuses a sync that would remove a dropped target.

Sync and plugin builds share target selection and renaming. Sync removes unmanaged collisions before rewriting references. Hook and MCP entries are lowered from the selected target state, never rediscovered, and their config must not reference a directory target sync failed to install. Invalid dependency hooks can retain the directories and outputs recorded in the lock rather than being pruned as removed.

See [target sync ownership](../target_sync/.context/CONTEXT.md) and [resolution](../resolve/AGENTS.md).

`lock::write` files each record in `mars.lock` or `.mars/machine.lock` by the targets `mars.toml` names, so `finalize` and every other `publish` caller passes `project_targets(&config)`; a writer that passes something else moves records between files. See [lock contracts](../lock/.context/CONTEXT.md).
